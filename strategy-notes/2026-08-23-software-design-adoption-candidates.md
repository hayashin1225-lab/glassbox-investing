# Glassbox ソフトウェア設計 採用候補整理

Status: Working Note / Not Canon
Date: 2026-08-23
Scope: 現時点までの対話、Issue #13 調査結果から得た示唆、既存の Working Ledger を踏まえたソフトウェア構造の採用候補

---

## 0. この文書の目的

本書は、Glassbox Investing の実装に入る前に、これまでの会話で形成された設計候補を一度まとめ、後続の人間判断に渡すための作業メモである。

ここで扱うのは**採用候補**であり、正本ではない。

市場検証、データライセンス確認、法務確認、実装検証、Issue #13 の追加調査によって変更・撤回する前提で保存する。

本書が答えようとする問いは次のとおり。

> Glassbox を「AI株診断」でも「四季報の再発明」でも「予想屋」でもなく、再現可能な銘柄査読ソフトウェアとして作るなら、どのような内部構造・レポート構造・更新方式が有力か。

---

# 1. 製品の中心定義

## 1.1 採用候補：銘柄を管理せず、銘柄を査読する

Glassbox の対象は銘柄そのもの。

扱う候補:

- 企業の収益構造
- 財務健全性
- キャッシュフロー
- バリュエーション
- 株価の現在位置
- 決算・業績修正・配当等の企業イベント
- 金利・為替・商品価格・業種指数等の外部環境
- 市場で注目されている論点
- その論点を支持する証拠
- その論点を弱める証拠
- 未確認事項
- 何が変われば現在の見方を再査読すべきか

扱わない候補:

- 推奨銘柄一覧
- Buy / Sell / Strong Buy 等の方向付け
- 目標株価
- ポートフォリオ管理
- 保有比率管理
- 個人の取得価格・資産額・リスク許容度を前提にした助言
- 発注・仲介

基本線:

> **銘柄を管理しない。銘柄を査読する。**

# 2. 価格納得感を作る三層

現時点で有力なのは、以下の三層。

## 2.1 第1層：レポート項目

ユーザーが最も直接的に価値を感じる層。

方向性:

- 四季報的な基礎情報は必要十分に押さえる
- 既存製品の良い項目は真似る
- ただし情報量競争には行かない
- Glassbox 独自項目は「査読」に集中させる

要するに、

> **基礎情報 × 独自査読項目のハイブリッド**

とする。

## 2.2 第2層：査読アルゴリズム

商品の中核。

数字を並べるだけではなく、

> **どの数字を、どの条件で、どう解釈可能な状態へ変換するか**

を決定論的に処理する。

AIを使わず再現可能な部分は、可能な限りコードへ寄せる。

理想状態:

> **同じ入力データ + 同じ Engine version = 同じ査読結果**

## 2.3 第3層：AI引き継ぎプロンプト

Glassbox 自身で断定できない部分、自然言語文書の意味理解、さらに深い調査が必要な部分を、外部AIへ安全に渡す。

渡す候補:

- 現在確認済みの事実
- 使用した数値と期間
- 主要論点
- 支持材料
- 弱める材料
- 未確認事項
- 次に調べるべき一次資料
- 禁止事項（売買方向を返さない等）

Glassbox 自身が巨大な汎用調査AIになる必要はない。

# 3. レポートの基本構造

## 3.1 採用候補：長い表ではなく「論点を圧縮」する

ユーザーに30〜50指標をそのまま見せても理解しにくい。

一方、単一総合点へ圧縮すると、異なる尺度を一つの数字へ潰してしまい、

- 78点だから買ってよい
- 42点だから悪い銘柄

のような誤読を誘発しやすい。

そこで採用候補は、**評価の集約ではなく論点の圧縮**。

表面:

> **この銘柄を見るなら、いま重要なのはこの3点です。**

裏側:

- 多数の分析器
- 多数の数値
- 複数の比較軸
- 適用可否判定
- 失敗条件判定
- 出典管理

を動かす。

原則候補:

> **Glassbox は銘柄を採点しない。銘柄を見るための視野を圧縮して提示する。**

# 4. 分析手法を「採点器」ではなく「検出器」として扱う

## 4.1 採用候補：Detector Architecture

Issue #13 で調べている古今の分析手法は、「どれが最強か」を決めるためではなく、異なる異常・特徴・論点を検出する部品として扱う。

例:

- Piotroski F-score
- Altman Z-score
- Beneish M-score
- Sloan accruals
- DuPont
- ROIC
- margin trend
- FCF conversion
- leverage / interest coverage
- PER / PBR / EV/EBITDA
- historical valuation range
- peer comparison
- drawdown
- relative performance
- volatility
- event calendar
- macro sensitivity

これらを単一スコアへ加算しない。

各手法は、

> **この銘柄について、どの観点を検出できるか**

という役割を持つ。

## 4.2 Detector の標準メタデータ候補

各 Detector は、単なる出力値だけでなく以下を持つ。

1. `signal`
   - 何を検出したか
2. `applicability`
   - この企業・業種・期間に適用してよいか
3. `failure_modes`
   - どの条件で誤判定しやすいか
4. `evidence`
   - 判定に使った一次データ
5. `period`
   - 対象期間
6. `confidence_basis`
   - 信頼度そのものではなく、判定根拠の完全性
7. `sector_adjustment`
   - 業種補正の有無
8. `engine_version`
   - どのルール版で処理したか

重要なのは、Glassbox が**指標を盲信しない**こと。

原則候補:

> **Glassbox の価値は「正しい指標を選ぶこと」ではなく、各指標が何を検出でき、何を検出できないかまで管理すること。**

---

# 5. 正規化レイヤーは中核候補

## 5.1 採用候補：Normalization Layer

分析ロジック以前に、入力データの意味を揃える必要がある。

候補処理:

- 会計年度の正規化
- 四半期 / 通期の区別
- IFRS / J-GAAP / US-GAAP差異の扱い
- 継続事業 / 非継続事業
- 株式分割・併合補正
- EPSの分母差異
- 実績 / 会社予想 / 市場予想の区別
- 通貨・単位の統一
- M&A前後の比較可能性
- セグメント変更
- 会計方針変更
- 一過性損益の分離候補
- restatement / 過年度修正

ここが崩れると、その後の精密な分析も全部誤る。

従って実装優先度は高い。

> **検出器より前に、比較可能なデータを作る。**

# 6. Evidence Engine と Interpretation Layer を分離する

## 6.1 採用候補：二層構造

### A. Deterministic Evidence Engine

担当:

- 数値取得
- 正規化
- 計算
- 期間比較
- 閾値判定
- 異常検出
- バリュエーション比較
- 価格位置
- イベント日数
- 相対騰落
- Provenance

ここはAIを使わず処理することを原則とする。

### B. Narrative / Interpretation Layer

担当候補:

- 決算資料・IR文書から主要論点を抽出
- 市場で語られている期待の整理
- なぜ利益が変化したかの意味整理
- 一過性要因の自然言語説明
- 数値と物語の対応付け
- ユーザー向け自然言語への圧縮

ここはAI利用候補だが、AI出力を一次事実として扱わない。

AIが論点を見つけた場合、可能な限り Evidence Engine 側の数値・一次資料へ戻して裏付ける。

候補原則:

> **AIは数値を決めない。AIは論点を見つけ、Evidence がそれを支えるかを確認する。**

# 7. レポートの表示層

## 7.1 最上段：30秒ビュー

候補:

- 銘柄名 / コード
- 最終データ更新時刻
- Engine version
- 「いま見るべき3点」
- 重大な反証候補
- 未確認点
- 次の重要イベント

ここでは情報量を抑える。

目標:

> **数十個の内部検出結果を、人間が理解できる数個の論点へ圧縮する。**

## 7.2 詳細ビュー

最上段で気になった論点を展開する。

候補セクション:

1. 企業カルテ
2. Fundamental Review
3. Valuation Review
4. Price Context
5. Event & Market Context
6. Counterevidence
7. Unknowns
8. Sources / Provenance
9. AI引き継ぎ

## 7.3 企業カルテ

四季報的基礎はここへ置く。

候補:

- 企業概要
- 主要事業 / セグメント
- 売上
- 営業利益
- 純利益
- EPS
- 営業利益率
- 営業CF
- FCF
- 自己資本
- 有利子負債
- ROE / ROIC
- PER / PBR
- 配当利回り
- 株主還元
- 株価レンジ
- 主要競合

ただし基礎情報そのものを商品核にしない。

# 8. Fundamental Review

## 8.1 採用候補

- 売上成長と利益成長の分解
- 利益率の推移
- 本業利益と最終利益の乖離
- EPS成長の源泉
- 営業CF / FCF の質
- 利益とCFの乖離
- 運転資本変動
- 有利子負債
- 利払い余力
- 株主還元余力
- 希薄化
- 自社株買い
- 一過性要因
- 会計上の異常候補

結果は「良い / 悪い」だけではなく、

> **何がそう見せているのか**

まで分解する。

例:

> 純利益は大幅増益だが、営業利益は減益。一過性の営業外要因が最終利益を押し上げている。

---

# 9. Valuation Review

## 9.1 採用候補

- PER
- PBR
- EV/EBITDA
- FCF yield
- 配当利回り
- 過去レンジ
- 同業比較
- 成長率との整合
- 収益性との整合

重要原則:

> **良い会社と、良い価格を分ける。**

一つの適正株価へ集約しない方向が有力。

DCF等は内部補助として使う余地はあるが、仮定依存性が高いため、単一の「理論株価」として前面表示するのは慎重にする。

# 10. Price Context

## 10.1 採用候補：チャートを予測ではなく文脈に使う

候補:

- 52週高値 / 安値
- 直近高値からのドローダウン
- 20 / 60 / 200日移動平均との位置
- 出来高変化
- ボラティリティ
- 下落速度
- TOPIX / 日経等との相対騰落
- 業種指数との相対騰落

ここで「買い時」「押し目買いシグナル」は出さない。

代わりに、典型的な査読テンプレートとして、

> **安くなったのか、悪くなったのか。**

を置く。

## 10.2 下落査読は Engine 全体ではなくテンプレートの一つ

同じ思想で、以下も作れる。

- 上がった
  - **良くなったのか、期待だけ膨らんだのか**
- 増益した
  - **稼ぐ力が強くなったのか、一過性なのか**
- 増配した
  - **余裕が増えたのか、無理して配っているのか**
- 高ROE
  - **事業が強いのか、レバレッジなのか**
- 低PER
  - **割安なのか、悪化を織り込んでいるのか**

より一般化した Engine の役割候補:

> **表面に見える変化を、別の独立証拠で査読する。**

# 11. Event & Market Context

## 11.1 採用候補：Event Risk / Information Change Risk

予測ではなく、

> **もうすぐ情報セットそのものが変わる**

ことを示す。

候補:

- 次回決算までの日数
- 直近決算からの日数
- 業績予想修正
- 配当・権利日
- 株主総会
- 自社株買い
- 増資
- 大型IR
- 製品発表等

例えば、

> 次回決算まで4日。現在の査読は前回開示情報に基づく。

という表示は、売買助言をせず実用性を出せる。

## 11.2 市況の扱い

候補:

- 金利
- 為替
- 原油
- 商品価格
- 業種指数
- 景気指標

使い方:

> **企業固有要因と、市場全体・業種全体要因を分離する。**

業種ごとに見る外部変数を変える。

# 13. 「重要な3点」をどう選ぶか

## 13.1 最重要の未解決設計

総合点を避けても、最終的には大量の Detector から何を前面表示するかを決める必要がある。

ここには別種の編集判断が発生する。

候補評価軸:

- 異常度
- 前年 / 過去平均からの変化幅
- 同業平均との差
- 企業価値への影響範囲
- 一過性か継続性か
- 次回イベントまでの近さ
- データ完全性
- ユーザーが通常見落としやすい論点か
- 複数 Detector が独立に同じ論点を支持しているか

ただし、これらをそのまま単一数値へ足し上げる必要はない。

## 13.2 候補：Priority Router

内部で Detector output を整理し、

- 重要論点
- 補助論点
- 背景情報
- 無効 / 適用外

へルーティングする。

ユーザーには「順位の根拠」を追跡可能にする。

例:

> この論点が前面に出た理由
> - 営業利益率が3年中央値から大幅低下
> - 営業CFも同方向に悪化
> - 同業平均との差も拡大
> - 次回決算まで12日

この説明可能性が、単なるAI要約との差別化候補になる。

# 14. Provenance は全層の横串

## 14.1 採用候補

全数値・判定・説明に可能な限り以下を付与する。

- Source
- Source type
- Publication date
- Period
- Actual / Company Forecast / Consensus
- Currency
- Unit
- Calculation formula
- Normalization applied
- Detector version
- Engine version

UIでは最初から全部見せなくてよいが、ユーザーが掘れば確認できるようにする。

これは「AI幻覚なし」をコピーではなく機能に変える。

# 15. Engine versioning

## 15.1 採用候補：Glassbox Engine 2026 / 2027

データと方法論を分けて更新する。

### データ

- 日次 / 決算 / イベントに応じて更新

### Engine

- 方法論は版管理
- 過去の査読を後から新ルールで黙って書き換えない

候補表示:

- `Data as of: 2026-08-23`
- `Glassbox Engine: 2026.1`
- `Rule Set: 2026`

候補販売モデル:

- Glassbox 2026 は買い切り
- 2026 のデータ更新・不具合修正は継続
- 2027 で新 Detector、業種補正、アルゴリズム改善を提供
- 旧版を停止しない

商品名自体は単に `Glassbox` とし、内部・レポート上で `Engine 2026` を表示する案が有力。

# 16. AI利用方針

## 16.1 AIを使わない方がよい領域

- 財務数値計算
- YoY / QoQ
- 比率計算
- PER / PBR等
- 過去レンジ
- 相対騰落
- 移動平均
- イベント日数
- 閾値判定
- 出典・期間管理

## 16.2 AIを使う候補領域

- IR文書の論点抽出
- ニュースの意味整理
- 市場ナラティブ抽出
- 数値に対応する説明候補生成
- 未確認事項の列挙
- AI引き継ぎプロンプト生成

## 16.3 実行タイミング候補

毎クリックAI実行ではなく、

> データ更新
> → Detector 実行
> → 必要な銘柄だけ AI Narrative Layer 実行
> → 検証済み JSON 保存
> → ユーザーアクセス時は保存済み結果を表示

とする候補。

利点:

- 高速
- 安価
- 同時点なら全ユーザーで同じ表示
- 監査可能
- 実行時AI揺らぎを抑制

# 18. 体験版との接続

有力候補:

> **任意の1銘柄を、製品版と同品質で1回だけフル査読**

理由:

- 機能制限版では製品価値が伝わらない
- 日数制限では利用タイミングと噛み合わない
- レポート構造そのものが価格納得感の中心

体験で見せるもの:

- 30秒ビュー
- 重要論点
- Fundamental Review
- Valuation Review
- Price Context
- Event Context
- Provenance
- AI引き継ぎ

製品版との差は品質ではなく、**査読可能回数**に置く方向が有力。

# 19. データライセンスは早期確認事項

## 19.1 未解決

「APIで取得できる」ことと、

- 商用利用できる
- 保存できる
- ユーザーへ再表示できる
- 派生指標を販売できる

ことは別。

四季報的基礎情報を製品へ入れるなら、データ供給元のライセンス条件でUI・原価・製品価格が変わる。

実装前の早期確認候補:

- 株価
- 財務
- コンセンサス
- 企業イベント
- 業種指数
- 金利 / 為替 / 商品価格

ここは設計の後工程ではなく、初期アーキテクチャ制約として扱うべき可能性が高い。

# 24. まとめ

現時点で最も筋が通っている Glassbox の姿は、単なる財務情報サイトでも、AIによる銘柄診断でも、予想ソフトでもない。

内部では多数の成熟した分析手法を動かすが、それらを一つの「何点」という数字へ潰さない。

各分析手法を Detector として使い、

- 何を検出したか
- どの条件で使えるか
- どんなとき間違えるか
- 何を根拠にしたか

を管理する。

その上で、ユーザーには大量の内部計算をそのまま見せず、

> **この銘柄を見るなら、いま重要なのはこの3点です。**

という形へ圧縮する。

必要ならそこから、数値、計算式、期間、原資料、Detector、AI深掘りへ降りられる。

現時点の設計候補を一文に圧縮すると、

> **Glassbox は銘柄を採点するソフトではなく、再現可能な検出器群で銘柄を多面的に査読し、ユーザーがまだ見ていない可能性の高い観点を、根拠まで辿れる形で圧縮提示するソフトウェアである。**

この文自体も正本ではなく、今後の実装・市場検証・法務確認のための設計仮説として扱う。
